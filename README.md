# E-commerce Order RFM User Segmentation Analysis
电商店铺订单数据分析：RFM 用户分层与 GMV 结构

## 项目亮点

- **真实公开数据**：基于 Heywhale 公开电商订单数据集，47.2 万条订单明细、32.9 万个订单、17.5 万用户、6 个店铺、9 个流量渠道，时间跨度 2024-01 ~ 2026-06。
- **完整分析链路**：Python / Pandas 清洗 → MySQL 建表与口径视图 → SQL 计算指标 → 8 张结果表 → 自包含 HTML 报告，覆盖从原始数据到业务结论的全流程。
- **口径先行、只定义一处**：「成交 = 订单状态已完成」「用户 / 订单 / 明细的去重键」「近 12 个月窗口」「中位数分档」全部固定在 `sql/00_schema.sql` 的 4 个视图里，各指标文件只引用、不重复定义。
- **RFM 八分层**：把 16.8 万成交用户按 R / F / M 分成 8 类人群，对应「保持 / 发展 / 挽留 / 低成本触达」四类运营动作。
- **清洗即校验**：把数据字典里的质量结论落成 29 项对账检查，清洗与指标两个环节都能复现结论。

## 项目概览

本项目基于公开电商店铺订单明细数据，构建 RFM 用户分层与 GMV 结构分析。覆盖数据清洗与质量校验、MySQL 口径建模、SQL 指标计算、用户分层与业务洞察、HTML 报告呈现，适合作为数据分析 / 数据运营岗位的简历项目。

数据范围 2024-01-01 ~ 2026-06-30，共 912 天、47.2 万条订单明细；观察点取数据末日 2026-06-30，RFM 窗口取近 12 个月（2025-07-01 ~ 2026-06-30）。

## 数据集说明

数据来源为 Heywhale 公开数据集「某电商平台店铺订单明细」：
https://www.heywhale.com/mw/dataset/6ac4f3404c403036b9ebb17c

原始数据 472,481 行 × 14 列，一行代表一个订单商品明细（订单 × 商品），主键为 `订单id` + `商品id`（联合唯一）。字段说明：

| 列名 | 说明 | 单位 |
|:--|:--|:--|
| 订单id | 订单唯一标识，`O` + 7 位序号 | |
| 店铺id | 店铺唯一标识，st001 ~ st006 | |
| 日期 | 下单日期，含 `0:00` 时刻 | |
| 订单状态 | 已完成 / 已取消 / 已退款 / 已发货 / 待发货 / 待付款 | |
| 流量渠道 | 自然搜索 / 付费搜索 / 信息流广告 / 私域会员 / 平台活动 / 其他渠道 / 直播推广 / 直播自然流 / 平台会员 | |
| 数量 | 明细购买件数，1 ~ 18 | 件 |
| 折扣率 | 实际只取 0 / 1，是折扣标记而非折扣比例 | |
| 明细金额 | 该明细实际成交金额 | 元 |
| 成本价快照 | 下单时点的单位成本（同一商品随日期变动） | 元 |
| 用户id | 用户唯一标识，前缀为平台代码 TM / DY / PDD / JD / WX / XHS | |
| 佣金率 | 平台佣金比例，全表 12 个取值 | 比例 |
| 商品id | 商品唯一标识，共 1,320 个 | |
| 商品成交单价 | 该明细的商品单价（同一商品随日期变动） | 元 |
| 总成本 | 该明细总成本 = 成本价快照 × 数量 | 元 |

数据质量要点（完整校验见 `doc/数据说明.md` 与 `data/metrics/dq_校验结果.csv`）：

- **缺失**：仅 `用户id` 缺失 18,015 行（已取消 17,996 + 待付款 19），未成交订单没有用户标识；其余 13 列 0 缺失
- **重复**：完全重复行 0 条；`订单id` + `商品id` 联合重复 0 条
- **字段间逻辑**：`总成本 = 成本价快照 × 数量` 472,481 行全部成立；`明细金额 = 商品成交单价 × 数量 × 折扣率` 仅 81.84% 成立（实际成交价还含未记录的其他优惠）
- **归属**：一个 `用户id` 只出现在一个店铺内；一个 `订单id` 只对应一个店铺、一个用户

## 数据清洗流程

1. 读取原始 CSV（GBK 编码）
2. 删掉无用户标识的行 18,015 行（已取消 17,996 + 待付款 19）——这 ≠「删未成交订单」，已取消 / 已退款 / 已发货里带 `用户id` 的行仍在表内
3. 校验字段：缺失值、重复值、字段间逻辑、归属关系、枚举与数值范围
4. 输出 `data/订单表_clear.csv`（454,466 行）

「成交」的口径不在清洗层施加，由 `sql/00_schema.sql` 的 `v_成交明细` 定义。

## 指标口径说明

- **统计对象与去重键**：用户按 `用户id`，订单按 `订单id`，明细按 `订单id` + `商品id`
- **业务状态**：成交指订单状态「已完成」，已取消 / 已退款 / 待付款 / 待发货 / 已发货不计入
- **时间边界**：月为自然月，RFM 窗口为截止观察点（2026-06-30）的近 12 个月
- **单位**：金额 元，人数 人，比率 %
- **分档阈值**：R / M 取窗口中位数（本数据 R = 160 天、M = 207 元），F ≥ 2 为复购；观察点与窗口长度定义在 `sql/00_schema.sql` 的 `v_用户RFM`，是该文件里唯一需要改的配置，本次运行实际取值见 `data/metrics/rfm_阈值.csv`

RFM 八分层命名与策略方向：

| 分层 | 人群 | 策略 |
|:--|:--|:--|
| 近-高-高 | 重要价值客户 | 保持 |
| 近-高-低 | 一般价值客户 | 保持 |
| 近-低-高 | 重要发展客户 | 发展 |
| 近-低-低 | 一般发展客户 | 发展 |
| 远-高-高 | 重要保持客户 | 挽留 |
| 远-高-低 | 一般保持客户 | 挽留 |
| 远-低-高 | 重要挽留客户 | 挽留 |
| 远-低-低 | 一般挽留客户 | 低成本触达 |

## 业务洞察

### 1. GMV 高度集中在少数高价值人群

- **发现**：重要价值客户 12,605 人（占用户 14.40%）贡献了 34.44% 的 GMV，人均 841 元。
- **解释**：用户价值分布高度不均，头部人群是 GMV 的主要来源，资源不应平均撒在长尾。
- **可执行动作**：对「近-高-高」人群做保持策略（会员权益、专属服务、新品优先），维持其活跃度。
- **可验证指标**：重要价值客户数、其 GMV 占比、人均 GMV。

### 2. 一批高价值用户正在流失，值得优先召回

- **发现**：重要挽留 + 重要保持共 19,250 人，对应 32.3% 的 GMV，平均已 223 ~ 253 天没有成交；两者人均 GMV 分别为 465 / 722 元。
- **解释**：这批人历史消费能力强，但已长时间未回购，属于「可召回的高价值人群」，比唤醒低价值长尾更划算。
- **可执行动作**：分层召回——优先用大额券 / 新品通知 / 专属客服召回人均更高的重要保持客户。
- **可验证指标**：该人群回购率、召回后 GMV、平均 R 是否下降。

### 3. 大量用户已沉睡，长尾价值极低

- **发现**：成交用户 168,360 人中，80,813 人近 12 个月没有成交；两个低价值分层（一般挽留 / 一般发展）人均 GMV 只有 104 / 106 元，约为高价值人群（841 元）的 1/8。
- **解释**：长尾人群投入产出比低，不值得投入与高价值人群同等的运营成本。
- **可执行动作**：对一般挽留 / 一般发展人群只用低成本触达（短信、自动化推送），不做人工重运营。
- **可验证指标**：沉睡用户数、低成本触达的唤醒率与边际 GMV。

### 4. 新客来源集中，可按渠道复盘投放结构

- **发现**：全周期累计新客 168,360 人，自然搜索（36,357，21.6%）、信息流广告（30,752，18.3%）、付费搜索（27,083，16.1%）三个渠道合计 55.9%；平台会员渠道仅 411 人（0.2%）。
- **解释**：搜索与信息流类渠道是拉新主力，直播与平台会员渠道贡献很小，渠道结构可用统一口径横向对比。
- **可执行动作**：把预算向新客质量更高的渠道倾斜，对贡献极小的渠道做缩减或专门优化。
- **可验证指标**：各渠道新客数、新客 GMV 贡献占比、月度新客数趋势。
